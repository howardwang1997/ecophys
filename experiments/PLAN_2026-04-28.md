# H20 Experiment Plan — 2026-04-28

## Context

Yesterday (2026-04-27) the BPTT gradient-checkpoint approach failed on
H20: `chunk=128 K=8` OOM'd at 95 GB just like default `chunk=24` (80 GB).
Root cause: `create_graph=True` in `conservative_forces` pins per-step
V-graphs through the `s_next.grad_fn` chain across checkpoint groups —
`torch.utils.checkpoint` cannot release them.

Two new branches landed tonight, attacking the problem from different
angles:

| Branch | Approach | Memory hypothesis | Gradient semantics |
|---|---|---|---|
| `feature/spatial-checkpoint` (Sprint 1, commit `f1a004a`) | Edge-batch `torch.utils.checkpoint` inside `StochasticPairwisePotential.forward` | Reduce per-step V intermediates from O(N×k) to O(B). Doesn't fix cross-step pinning. | Identical to default (verified by tests). |
| `feature/custom-autograd-step` (Sprint 2, commit `af49839`) | Custom `EcoMDStepFunction` wraps each `sim.step()` — forward in `no_grad`, backward locally rebuilds 1-step graph then drops it | Memory bounded by ONE step's V-graph regardless of chunk_steps. Definitive fix at the source. | **Differs** from default — explicitly detaches inputs at each step boundary, breaking the cross-step grad_fn chain. See "contamination" note in commit. |

Phase 1 of the loss-redesign batch is half-done (24/45 train, 0/45 eval).
The bal/ch/dm axes collapsed at chunk=24 (no info). The lf and te axes
(loss family + tail estimator) are the actually informative ones and
didn't run.

## Decision tree for the day

```

  ├─ if Sprint 1 unblocks chunk=64+ → both Sprint 1 and Sprint 2 are viable
  └─ if Sprint 1 doesn't help → Sprint 2 is the only path to chunk>24

              (only if Sprint 2 memory holds at large N)

```

## Key questions answered by this plan

1. **Memory**: which sprint actually unblocks chunk > 24 / N > 10K?
   (Phases A, B)
2. **Loss-noise hypothesis**: does increasing chunk_steps from 24 → 128
   (loss sees 7 → 111 returns) reduce 5-seed variance and improve mean?
   (Phase C)
3. **Loss design**: which loss family + tail estimator gives best
   reproducible 11-fact score? (Phase D)
4. **Significance vs published baselines**: does winner C4 + new loss
   beat GARCH(1,1)-t (5-7/11) and LM99 (5/11) with multi-seed CI?
   (Phase E — paper §5 core)
5. **Scaling**: does N=20K-50K with bounded memory help further?
   (Phase F)
6. **Universality**: does winner generalise across asset sets? (Phase G)

## Risks + fallbacks

| Risk | Probability | Fallback |
|---|---|---|
| Both Sprint 1 and Sprint 2 fail to unblock chunk>24 | Low | Stick with chunk=24, do Phase D + E as documented (loss design only). Memory ≠ bottleneck for our existing data. |
| Sprint 2 trains worse than default at chunk=24 (contamination matters in the wrong direction) | Medium | Phase C will reveal this. If Sprint 2 chunk=24 is dramatically worse than default chunk=24, run Phase D + E on default path with chunk=24. |
| Sprint 2 chunk=128 OOMs unexpectedly | Low if Phase B confirms bounded memory | Drop to chunk=64 |
| Phase D shows no loss design dominates | Possible | Means architecture is the bottleneck (not loss); needs follow-up sprint |
| Phase E mean ≤ GARCH 5/11 | Possible (already ~3/11 yesterday) | Reframe paper as "first differentiable simulator framework, comparable-to-GARCH 11-fact reproduction, with multi-asset + physics extensions GARCH cannot match" |
