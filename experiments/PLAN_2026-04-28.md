**Updated 2026-04-27 evening** after H20 commit `a016713` (Phase 1

## Context

Two big findings have re-shaped the day:

1. **BPTT gradient checkpointing failed** (yesterday): `chunk=128 K=8`
   OOM'd at 95 GB on H20 due to `create_graph=True` pinning V-graphs
   across `torch.utils.checkpoint` group boundaries. Two new sprints
   address this from different angles:
   - `feature/spatial-checkpoint`: edge-batch checkpoint inside
     `StochasticPairwisePotential.forward`. Same gradients as default.
   - `feature/custom-autograd-step`: per-step custom
     `EcoMDStepFunction`. Memory bounded by ONE step's V-graph.
     Different gradients from default (cleaner, no cross-step
     contamination).

2. **Loss redesign showed no improvement** (this evening, commit
   `a016713`): 45/45 Phase 1 configs trained + eval'd. All variants
   produce 2.67-3.33/11 mean across 3 seeds. **seed dominates** (seed1
   gets 5/11, seed0=2/11, seed2=3/11 across every loss variant). One
   notable: `w2_only` had **CI = [3.00, 3.00]** (zero variance across
   3 seeds) but mean is identical to others — Wasserstein cancels seed
   variance but doesn't help mean.

   Conclusion from H20 commit msg: **"Bottleneck is model capacity /
   training regime, not loss function."** The chunk axis was null in
   Phase 1 because all configs got batch-sed to chunk=24 yesterday
   under the OOM ceiling.

This v2 plan **drops Phase D (loss-design ablation already done)** and
adds **Phase H (architecture / training regime sweep)** to test the new
"capacity / regime" hypothesis. Phase C still matters because chunk
axis hasn't been tested at real chunk=128 yet.

## Decision tree (v2)

```
Phase A (10 min) — Sprint 1 memory test
Phase B (10 min) — Sprint 2 memory test
  ├─ if neither bounds memory at chunk=128 → Phase C dropped, Phase H first
  └─ if Sprint 2 bounds memory → Phase C runs

Phase C (3-4h) — Sprint 2 + chunk effect on real data (chunk=24 vs 64 vs 128)
  ├─ if chunk=128 mean ≥ chunk=24 mean +1.0 → loss-noise hypothesis confirmed,
  │      use chunk=128 in Phase H + E
  ├─ if chunk=128 std ≤ chunk=24 std × 0.7 → chunk reduces variance (paper finding),
  │      use chunk=128 in Phase H + E
  └─ if neither → loss-noise NOT the bottleneck either; bottleneck = capacity/regime
      → Phase H is critical

Phase H (3-4h) — Architecture / training-regime sweep at Phase-C-winner chunk
  ├─ if any variant pushes mean ≥ 5/11 → use as Phase E candidate
  └─ if all stay at ~3/11 → architecture hypothesis ALSO null; need deeper investigation

Phase E (2-3h) — Multi-seed CI on top 1-3 winners × 3 archs × 5 seeds (paper §5)
  Skip if Phase H gives no winner.

Phase F (1.5h) — N=20K, 50K scale validation (only if memory bounded)
Phase G (1h)   — Multi-asset universality (only if winner exists)
```

**Decision rules**:
- `chunk=128 mean - chunk=24 mean ≥ 1.0/11` → loss-noise hypothesis **confirmed**.
  Use chunk=128 for Phase H + E.
- `chunk=128 std ≤ chunk=24 std × 0.7` → chunk extends *reduces variance*
  (would be a real paper finding). Use chunk=128 for Phase H + E.
- Neither → chunk doesn't matter on Sprint 2 path either. Use chunk=24
  (cheaper) for Phase H. Loss-noise definitively NOT the bottleneck.

## Phase H — Architecture / training-regime sweep (~3-4h, ~36 configs) — NEW

**This is the new hypothesis test based on Phase 1's null result.**

The seed-dominant pattern (seed1 always 5/11) suggests **training is
exploring different basins per seed and finding varying-quality local
optima**. Test whether the following modify the answer:

| Group | Variants | × seeds | Configs | Hypothesis |
|---|---|---:|---:|---|
| `ph_lr` | lr ∈ {3e-4, 1e-3, 3e-3, 1e-2} | × 2 (seed 0, 1) | 8 | Optimization landscape access |
| `ph_iters` | n_iters ∈ {200, 400, 800} | × 2 (seed 0, 1) | 6 | Convergence vs Goodhart trade-off |
| `ph_init` | init_state_scale ∈ {0.05, 0.1, 0.5} × hidden ∈ {48, 96} | × 2 (seed 0, 1) | 12 | Initialisation basin |
| `ph_n_seeds` | Best lr × hidden × **10 seeds** | × 10 | 10 | Distribution of seed outcomes |
| **Total** | | | **~36** | |

Critical config: `ph_n_seeds_best × seed=1` should reproduce 5/11; if
several seeds produce 5/11 with the right (lr, hidden, n_iters), we have
a winner.

Interpretation:
- If best variant gives mean ≥ 5/11 across 10 seeds → architecture/regime IS the lever
- If still seed-dominated 2-5/11 → seed lottery is genuine (consider best-of-N at training time)

## Key questions answered by v2 plan

1. **Memory**: which sprint actually unblocks chunk > 24 / N > 10K? (A, B)
2. **Chunk effect on clean grads**: does chunk=24 → 128 (sim_returns
   7 → 111) actually improve 5-seed CI, or is loss-noise NOT the
   bottleneck? (C)

   shift the seed distribution toward 5+/11? (H — NEW)

   hidden, n_iters), what's the actual distribution of outcomes?
   Is seed1 a one-off or a robust attractor? (H sub-experiment)

   Phase E gives the answer if Phase H produces a winner.
