#### Pre-existing non-determinism finding (worth noting for future)

During B-α training-loop smoke I observed: two sequential `train_distributed`
calls in the same Python process with identical args produce IDENTICAL
loss at iter 0-3 but DIVERGE from iter 4+. This is NOT caused by my
changes — running `regime_kind='gru'` twice in a row reproduces the same
drift. Root cause: `ecomd/models/potentials.py:262` uses
`torch.rand(n, n, device=device)` without a generator for SPS edge
sampling, so accumulated process-state mutations between sequential calls
cause divergence. **Not a problem on H20** (each config runs in a fresh
torchrun process), but means in-process A/B comparisons during smokes are
unreliable. Switched B-α smoke to rely on the unit-test for the
regression check (which is rollout-level bit-exact).

## Session 2 (later morning) — SPS edge-sampling determinism fix

### Goal

User asked: can the `potentials.py:262` non-determinism noted in Session 1
be fixed? If so, do it.

### What was done

#### Threaded torch.Generator through StochasticPairwisePotential

- `ecomd/models/potentials.py` — added `_step_generator: torch.Generator |
  None = None` attribute on `StochasticPairwisePotential`; `_sample_edges`
  now does `torch.rand(n, n, device=device, generator=gen)` where `gen`
  is `getattr(self, "_step_generator", None)`. Falls back to global RNG
  when None (backward-compat for direct test callers that don't pass a
  generator).
- `ecomd/models/ecomd.py::EcoMDSimulator.step` — sets
  `pairwise._step_generator = generator` at the top of the inner-step
  loop, exactly where the `generator` kwarg is in scope. Both the K=0
  rollout path and the bptt_custom_function path benefit (Function's
  forward and backward recompute both call `sim.step(..., generator=...)`).
- Did NOT thread generator through `conservative_forces` or the
  `Potential.forward` signature — the setter pattern is single-touchpoint
  and avoids cascading kwarg changes across 5+ files.

#### Discovered a second, distinct non-determinism source: CPU BLAS multi-threading

Even after the SPS fix, in-process A/B `train_distributed('gru')` × 2 was
still diverging from iter 4+. Diagnosed via `torch.set_num_threads(1)`:
with single-threaded BLAS, the two runs are **bit-exact identical across
all 30 iters** (max loss diff = 0.00e+00). So the residual drift was from
floating-point reduction-order non-determinism in parallel matmul/sum
operations on CPU — a known PyTorch behavior, NOT a bug in our code.

**Implication**: future Mac smoke / in-process A/B tests should set
`torch.set_num_threads(1)` at the top of the script for bit-exact
reproducibility. H20 GPU runs are unaffected (each cfg runs in its own
process; the only relevant reproducibility is "same checkpoint resume
gives same continuation", which is unaffected by thread count).

### Results / findings

- **Edge-sampling fix verified**: 340/340 tests pass after the change. The
  bit-exact tests (`test_ss_prob_zero_preserves_baseline_bit_exact`,
  `test_gru_regression_bit_exact_to_legacy`,
  `test_ss_compatible_with_bptt_custom_function`) all still pass —
  meaning the fix didn't break any deterministic same-seed equality
  property.
- **CPU multi-threading is the residual non-determinism source**, not
  any other unsedeed RNG. Cross-checked: every other `torch.rand*` call
  in the v3 hot path (price_formation, integrator, init_state) already
  passes `generator=`. Only `potentials._sample_edges` was the gap.
- The fix DOES change numerical values vs pre-fix runs: previously,
  edge sampling consumed global RNG, so the same cfg+seed produced one
  trajectory; now it consumes the rollout's seeded generator, so the
  same cfg+seed produces a DIFFERENT (but reproducible-going-forward)
  trajectory. Past 089-099 results are still valid (published numbers),
  but a re-run of those configs at HEAD would produce slightly different
  numbers — close in distribution, not bit-exact.

### Open questions / blockers

- `ecomd_v2.py:135 _sample_edges` has the same pattern (module-level
  function, no generator). V2 path is no longer the primary architecture

- `nn.Parameter` and `nn.init.*` calls in module __init__ use the global
  torch RNG. This is the standard pattern across PyTorch — fine because
  `torch.manual_seed()` before sim instantiation deterministically
  reproduces param init.
