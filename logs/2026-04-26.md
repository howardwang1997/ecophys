### Diagnostic finding — the bug-level design choice

Drilled into trainer code and found near-bug-level issue:
- `chunk_steps=24, warmup_steps=16` ⇒ `sim_returns = traj.log_returns[17:]`
  is only **7 returns long**.
- Hill estimator k_frac×7 = 0-1 tail samples → pure noise.
- `leverage_sum(max_lag=20)` on length-7 → only computes lags 1-6.
- `zumbach_asymmetry_diff(coarse_window=30)` on length-7 → fact undefined.
- Estimator standard error 30-200% per rollout. K-rank averaging only
  shaves √K. The optimiser is chasing pure noise.

Why chunk was stuck at 24: `rollout_chunk` retains all per-step
activations + force trajectories in autograd graph with `create_graph=True`.
Memory linear in chunk_steps × N × layers. On 4-card H20 chunk≥48 N≥10K
OOM'd.

### Decisions

User confirmed merge feature/paper-a-solidify → main (ff-only), then
opened `feature/bptt-checkpoint`. Chose:
- BPTT grouped checkpointing K=8 (not per-step K=1)
- FULL loss redesign (W2 + MMD + Sinkhorn + quantile-tail + kurtosis +
  smooth_dev + LossBalancer)
- 100+ configs deep ablation
- ff-only merge to main

Mid-session user pointed out: **chunk=24 actually uses 85 GB on H20, not
my estimated ~30 GB**. Memory model off by 3×. Reverse-calibrated:
per-step memory ≈ 3.5 GB at N=10K stochastic_mlp + create_graph=True.

Three sources I had missed:
1. `StochasticPairwisePotential.forward` calls `self.net` twice (phi_ij
   AND phi_ji symmetrisation) — intermediates ×2.
2. `conservative_forces` uses `autograd.grad(V, s, create_graph=True)` —
   retains entire V autograd graph for ∇V's path → effective ×2.
3. PyTorch caching allocator reservation overhead.

CRITICAL CORRECTION: I had K direction backwards. **K = checkpointed
group size, peak HBM ∝ K × per_step. Smaller K saves more memory**.
Original Phase 4 N=50K K=16 would have been 280 GB peak (guaranteed
OOM). Fixed to K=4 → 70 GB peak (tight but fits).
