**Critical finding: BPTT gradient checkpointing does NOT save memory in EcoMD.**

Root cause analysis:
1. EcoMD's `step()` calls `torch.autograd.grad(u, s, create_graph=True)`
   to compute conservative forces from the learned potential.
2. BPTT checkpoint wraps groups of K steps in `torch.utils.checkpoint`.
   During backward, it recomputes the forward pass.
3. The recompute itself requires `autograd.grad` with `create_graph=True`,
   which must preserve the full computation graph → **all memory is
   re-allocated during recompute**.
4. Net effect: chunk=128 with K=8 checkpoint uses ~95 GB, same as
   chunk=128 without checkpoint. The K=8 → K-fold memory reduction
   predicted by the theory breaks because the forward pass itself
   requires gradient computation (higher-order autograd).

Calibration: baseline predicted 87 GB, measured 79.64 GB (ratio 0.92×).
Prediction model is accurate; the issue is specifically that the memory
model assumes forward pass stores no intermediate gradients, but
`autograd.grad(create_graph=True)` does.

### Decisions

1. **All chunk>24 configs OOM** on single H20 card (98 GB). Only
   `chunk_steps=24, bptt_checkpoint_every=0` fits at ~80 GB.
2. Batch-sed all 109 configs to `chunk_steps: 24, bptt_checkpoint_every: 0`.
   This collapses the `ch` ablation axis (chunk24/64/128 all become
   chunk24), but the remaining axes (lf, te, dm, bal) remain valid.
3. N=20K/50K/100K (Phase 4) are **not feasible** on single-card — they
   would need ~160/400/800 GB. Would require spatial sharding
   (`feature/spatial-checkpoint`) or multi-GPU tensor parallelism.
4. Phase 5 (multi-asset) remains feasible at N=10K chunk24.

### Key findings

1. **No loss-family variant beats 5/11** — worse than the C4 baseline's
   8/11 from the weekend batch. The loss redesign (4 families, new tail
   estimators, balance modes) did NOT improve stylized fact reproduction.
2. **All axes within noise of each other** — bal/ch/dm/te all produce
   3.0–3.3/11 mean. The only signal is that `w2_only` (Wasserstein-2
   only, no moment matching) is slightly more stable (CI = [3,3]).
3. **Seed variance dominates** — seed1 consistently gets 5/11 while seed0
   and seed2 get 2-3/11. Same pattern as the L-series multi-seed CI
   (experiment 025).
4. **BPTT/chunk axis is a null result** — after fixing all configs to
   chunk24_K0, the ch axis variants (chunk24/64/128) are identical runs
   (same effective config), confirming no difference.

### Diagnosis

The loss redesign was predicated on the hypothesis that better loss
functions would improve fact matching. Phase 1 shows this is not the
bottleneck — **the bottleneck is the model capacity / training regime**,
not the loss function. All loss variants converge to similar performance
because the 200-iter training with chunk=24 doesn't give the model enough
rollout length to meaningfully distinguish between loss functions.

## Open questions / next steps

1. **Spatial sharding** is the path to N>10K — need `feature/spatial-checkpoint`
   that shards the pairwise interaction across GPUs (peak ∝ B, not ∝ N).
2. **Phase 2/4/5 configs all use chunk24_K0** — Phase 2 (45 configs)
   and Phase 5 (9 configs) are immediately runnable but Phase 1 shows
   no clear winner to feed into Phase 2.
3. Consider **multi-GPU DDP with NPROC=4** per config for tighter eval CI.
4. Root cause of **high seed variance** (8/11 vs 2/11 same config) needs
   investigation — likely related to initialization or early-training
   instability.
