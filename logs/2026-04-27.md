**Critical finding: BPTT gradient checkpointing does NOT save memory in EcoMD.**

Root cause analysis:
1. EcoMD's `step()` calls `torch.autograd.grad(u, s, create_graph=True)`
   to compute conservative forces from the learned potential.
2. BPTT checkpoint wraps groups of K steps in `torch.utils.checkpoint`.
   During backward, it recomputes the forward pass.
3. The recompute itself requires `autograd.grad` with `create_graph=True`,
   which must preserve the full computation graph → **all memory is
   re-allocated during recompute**.
4. Net effect: chunk=128 with K=8 checkpoint uses ~95 GB, same as
   chunk=128 without checkpoint. The K=8 → K-fold memory reduction
   predicted by the theory breaks because the forward pass itself
   requires gradient computation (higher-order autograd).

Calibration: baseline predicted 87 GB, measured 79.64 GB (ratio 0.92×).
Prediction model is accurate; the issue is specifically that the memory
model assumes forward pass stores no intermediate gradients, but
`autograd.grad(create_graph=True)` does.

### Decisions

1. **All chunk>24 configs OOM** on single H20 card (98 GB). Only
   `chunk_steps=24, bptt_checkpoint_every=0` fits at ~80 GB.
2. Batch-sed all 109 configs to `chunk_steps: 24, bptt_checkpoint_every: 0`.
   This collapses the `ch` ablation axis (chunk24/64/128 all become
   chunk24), but the remaining axes (lf, te, dm, bal) remain valid.
3. N=20K/50K/100K (Phase 4) are **not feasible** on single-card — they
   would need ~160/400/800 GB. Would require spatial sharding
   (`feature/spatial-checkpoint`) or multi-GPU tensor parallelism.
4. Phase 5 (multi-asset) remains feasible at N=10K chunk24.
